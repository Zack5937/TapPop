# 红包随机分配设计与实现前审查 — 2026-10-03

选定 ORAO Classic VRF v2（固定 SDK 0.7.0 / Anchor 0.32.1），只接受该程序拥有且 PDA、seed、client、fulfilled 状态都匹配的随机账户。客户端 nonce 只区分请求，不是随机分配的熵。程序通过 CPI 创建全新的 VRF 请求，不接受已有随机结果。

## 流程

普通等额：总 raw units 必须整除份数，每人领取固定 raw amount；最后一份也严格相等。

拼手气：领取人先签名 reserve_lucky。原子创建 ClaimRecord PDA，绑定当前份次、领取人和全新 VRF seed，并向 ORAO 请求随机性。同一红包只允许一笔未完成预定，后续人等待它结算。VRF 履行后任何钱包可支付交易费调用 settle_lucky，代币只能转入被预定领取人的 ATA，不能改收款人或金额。不可取消、换 seed 或再次领取。剩最后一份直接获得余量，不收 VRF 请求费。

分配上限为 min(2 × remaining / remainingClaims, remaining − (remainingClaims − 1))，从 1 到上限均匀抽取，保留每份至少一个 raw unit。以已验证 VRF 熵和领域分离 hash 生成样本，并用拒绝采样避免取模偏差。总数与 token raw units 都使用整数。

## 威胁审查结论

- 创作者：无法提交中奖金额或熵，无法改已锁定的资产/份数，不能靠预知结果挑选已履行的 seed；链上验证新建随机账户。可建立多个红包、选择受众，不能承诺对此无操纵。
- 领取人：资格先锁定再公开结果；不可看结果重抽。permissionless settle 使拒绝提交结算不能阻止其他人将奖励发给其固定地址。
- 预请求/抢跑：别人预先占用 seed 会使请求失败且整笔预定回滚，不能将那个已知结果拿来领奖。重试需新 nonce；仍有可付费实施的拒绝服务风险。
- 排序：单笔进行中的 VRF 请求使后续剩余金额在前一笔结算前不可改写；区块生产者仍能排序领取交易。程序按钱包防重领，不防女巫多钱包，不宣称公平身份准入。
- 预言机：依赖 ORAO 程序及其配置/升级权限、履行节点门限和可用性。不是本项目中央支付服务器，但不是“无外部信任”。程序固定 oracle ID、PDA 与账户 owner，不能由前端替换成任意随机来源。
- 超时：普通红包到期可退未领余额；拼手气有已履行预定时必须先结算，避免创作者观察结果后截走金额。未履行预定在红包到期一小时后可整体退款并永久关闭红包，不允许保留余额继续重抽。预言机延迟/拒绝服务可能令该预定最终没有收益，这是公开的活性/退款取舍。
- 费用：红包不是商家支付；创建者付创建/托管租金，领取人付 ClaimRecord/ATA 租金、网络费和（需要时）VRF 费用，代结算者付其交易及 ATA 创建费。签名前必须单列并限制 VRF fee，不能暗中宣称领取零 Gas。

结论：不使用时间戳、公开 blockhash 或客户端随机数作为奖励随机性；按上述边界实施 VRF 预定/结算，依然需要合约集成测试、Devnet 部署与实际 ORAO 履行验收，不能当作审计通过。
